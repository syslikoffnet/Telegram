# Трассировка отправки: «Логирование» в настройках Pengram

## Зачем это понадобилось

Анимация отправки текстового сообщения «мигает» только на устройстве. Здесь нет
ни телефона, ни эмулятора, ни GL-контекста, поэтому четыре итерации правок
(`5cc832e`, `65f3785`, `2ea9586`, `ce1df9b`, `9f5c505`, `7917689`) делались по
исходникам и каждая следующая опиралась на догадку о том, что именно увидел
пользователь. Дифференцировать две правдоподобные причины — расхождение
геометрии overlay и строки либо внутристрочный crossfade текста — по коду
нельзя: обе дают одинаковую картинку «текст то появляется, то пропадает».

Поэтому в сборку встроен сборщик фактических данных с устройства:
`org.telegram.messenger.PengramSendTrace` и раздел «Логирование» в настройках
Pengram. Он пишет ровно те числа, по которым видно, кто и что нарисовал в каждом
кадре перелёта.

## Что собирается

Буфер кольцевой, 8000 строк, живёт в памяти процесса. Формат строки:

```
    123,4ms FRAME  n=17 p=0.34 alphaP=0.85 ...
```

| Тег | Где пишется | Что показывает |
| --- | --- | --- |
| `SEND`/`ANIM` | `ChatListItemAnimator.animateAddImpl` | появлялась ли новая строка, создан ли перелёт и почему нет (`perfOk`, `nearEnough`, `transY`, `listH`), своё сообщение или входящее (`out`, `sending`), длина текста |
| `CTOR` | конструктор `TextMessageEnterTransition` | `bail=blocks\|edit_field\|empty_edit_text` — перелёт не создан; `ok` — что захвачено: длины текста поля ввода, сообщения и текста без U+200B (`zwsp`), `crossfade`, `spans`, высота стеклянного острова (`islandH`), компенсация отступа (`targetPad`), прямоугольник пузыря строки |
| `START` | `TextMessageEnterTransition.start` | запустится ли аниматор (`willRun`) |
| `FRAME` | `onDraw` overlay, каждый кадр | прогресс (`p`, `alphaP`, `pX`), где overlay рисует пузырь (`bubL/bubT/bubR/bubB`) и где пузырь строки (`cellBub`), где overlay рисует текст (`textX`, `textY`) и где строка на самом деле (`rowTop`), подавлена ли строка (`suppressed`), альфа строки, клип (`clipBottom`, `listBottom`) |
| `DRAW` | вход в `ChatMessageCell.drawMessageText` | **кто рисует текст** — `who=overlay\|cell`, `origin`, `alpha`, число блоков вёрстки, запасной путь без стилей (`plain`), `suppressed`, `viewAlpha`, `timeAlpha`, `ignoreAlpha`, внутристрочный crossfade (`animText`, `animProg`), видимость, смещение, координаты текста, id сообщения |
| `SKIP` | ранние выходы `drawMessageText` | текст в этом кадре не нарисован вовсе: `reason=no_blocks` или `reason=alpha_zero` |
| `CELL` | `setEnterTransitionInProgress`, `finishEnterTransition` | смена подавления строки, поколение (`gen`, `matched`) — по нему видно, не снимает ли подавление чужой перелёт |
| `LAYOUT` | `MessageObject.generateLayout` | пересборка вёрстки: `softWrap`, число U+200B, длина, блоки, `hasLayout`, `layoutCreated`, `empty`, `failed`, `failures`, запасной путь, `spans` |
| `FINISH` | `finishTransition` | прогресс на момент завершения и число кадров |

Шапка отчёта дополнительно фиксирует: версию сборки (`PengramVersion.report()`),
класс производительности, плотность и размер экрана, настройки `inputAnimation` и
`sendTextStyle`, сигнатуру жидкого стекла поверхности ввода
(`PengramGlassSkin.signature(SURFACE_INPUT)`) и разрешённость рефракции — именно
стекло меняет высоту «острова» ввода, из которой считается цель перелёта.

**Текст сообщений в лог не попадает.** Пишутся только длины, id и геометрия —
отчёт можно пересылать без риска раскрыть переписку.

## Как пользоваться

1. Настройки Pengram → Основные → «Логирование» → включить
   «Логировать отправку сообщений». Включение сразу очищает буфер.
2. Отправить несколько сообщений в любой чат: обычное, с длинным словом или
   ссылкой (мягкая вёрстка ставит U+200B), со стилем текста (жирный — он даёт
   `spans` и включает официальный crossfade). Желательно повторить то, на чём
   мигание воспроизводится.
3. Рядом в строке «Отправить лог» видно число собранных строк — если оно растёт,
   сбор идёт.
4. «Отправить лог» сохраняет отчёт в `files/logs/pengram-send-trace-<дата>.txt`
   и открывает системный лист отправки (файл отдаётся через штатный
   `FileProvider` приложения, каталог `logs/` описан в `provider_paths.xml`).
   Если отправить нечем, текст копируется в буфер обмена, а путь показывается
   всплывающим уведомлением.
5. «Очистить лог» обнуляет буфер, не выключая сбор.

## Цена

По умолчанию выключено. Каждая точка замера начинается с
`PengramSendTrace.enabled()`, а сам `log()` повторно проверяет флаг и выходит
сразу, — при выключенном сборе не выполняется ни форматирование, ни запись.
`enabled()` читает `PengramConfig.getIntCached`, то есть кэш в памяти процесса,
без обращения к `SharedPreferences` на каждый кадр.

Буфер ограничен 8000 строк: длинная сессия вытесняет самые ранние записи,
память не растёт неограниченно.

## Проверки

`scripts/test-pengram-send-trace.py` (11 проверок) держит контракт:

- сбор выключен по умолчанию, флаг хранится как `int` (`putBoolean` у
  `PengramConfig` закрытый), `log()` выходит сразу при выключенном сборе;
- буфер ограничен, время монотонное (`SystemClock.uptimeMillis`), числа
  форматируются в `Locale.US` — иначе запятая вместо точки ломает разбор;
- файл пишется в `files/logs/`, и этот каталог действительно описан в
  `provider_paths.xml` (иначе `FileProvider` бросит исключение);
- authority берётся из `applicationId`, а не зашит строкой; при отказе шаринга
  лог копируется в буфер обмена;
- в шапке есть все параметры, от которых зависит мигание;
- **ни одна запись не выполняется без проверки `enabled()`** — проверяется
  поиском guards в окне перед каждым вызовом `log(`;
- каждый тег пишет те поля, ради которых затевалась трассировка (в том числе
  `who=overlay|cell` — ключевой признак двойной отрисовки);
- строки настроек существуют, id уникальны, тумблер заведён через `tgCheck`
  (иначе строка не перепривязывается) и пересобирает список, чтобы строка
  «Отправить лог» показала актуальное число строк;
- строки интерфейса есть в `values-ru` и `values`;
- **трассировка не меняет поведение отправки**: `drawBitmaps` по-прежнему
  `false`, условие официального crossfade не тронуто, `start()` по-прежнему не
  глушит ячейку.

## Что показал первый лог с устройства

Xiaomi 2311DRK48G, Android 14 (SDK 34), плотность 3.0, 1220x2562,
`performanceClass=2`, `inputAnimation=1`, `sendTextStyle=1` (жирный),
`glassRefraction=false`. Четыре отправки, 3591 строка трассы.

| Наблюдение | Вывод |
| --- | --- |
| в каждом кадре перелёта `DRAW who=cell alpha=1.0` **и** `DRAW who=overlay alpha=0.08…1.0` с одним `id` | содержимое строки рисовали двое одновременно — причина мигания |
| `FRAME n=1 bubT=1391` при `rowTop=1189`, `transY=169`, `cellBub=[27,3,…]` → пузырь строки 1361…1530 | копия overlay и копия строки в начале полёта расходятся на ~30 px |
| `FRAME n=32 bubT=1193 bubB=1362` при строке 1192…1361, `textX/textY` совпадают | overlay приземляется ровно на строку: глушение безопасно, передача бесшовная |
| `islandH=133.0` при `dp(44)=132`, `targetPad=1449` при `listPadBottom=1450` | гипотеза о промахе цели из-за высоты стеклянного острова **не подтвердилась** |
| `CTOR ok … crossfade=true spans=true` при равных длинах текста на всех четырёх отправках | ветвь crossfade включал автоматический стиль «жирный»: сущность есть у каждого сообщения |
| `animText=false` во всех кадрах, хотя `animProg` после перелёта идёт 0→1 | внутристрочный crossfade текст не трогает: он требует `animateMessageText` |
| `CTOR ok … editTextLen=4 msgTextLen=3 unwrappedLen=4 zwsp=-1` | `pengramUnwrappedText()` вернул устаревший «оригинал» — отдельный баг, исправлен |
| `SKIP reason=alpha_zero drawOnlyText=true` только в первых двух кадрах | копию строки у overlay в них закрывает копия поля ввода с альфой `1 - alphaProgress` |
| `ANIM created=true perfOk=true nearEnough=true`, `START willRun=true`, `FINISH progress=1.0` | перелёт создавался и доходил до конца на всех четырёх отправках, отказов не было |
| `LAYOUT id=-211521…-211524 layoutCreated=true failures=0 fallback=false` | вёрстка отправленных сообщений создавалась нормально, запасной путь не срабатывал |

Диагноз и правка — в `docs/pengram-send-text-visible.md`.

Отдельно: первый лог печатал время в секундах с подписью `ms`
(`(uptimeMillis - startedAt) / 1000f`), поэтому «5.1ms» означало 5100 мс.
Единицы исправлены, длительность перелёта по новому логу читается напрямую.

## Чего этот документ не утверждает

Сборщик не чинит мигание — он собирает данные. Причина названа по первому же
реальному отчёту с устройства (раздел выше), но сама правка на устройстве не
проверялась: ни телефона, ни эмулятора, ни GL здесь нет. Трассировка остаётся в
сборке — следующий лог покажет, что в кадрах перелёта `suppressed=true` и
`who=cell` во время полёта отсутствует. Отчёт не снимается автоматически и никуда
не отправляется без явного действия пользователя.
