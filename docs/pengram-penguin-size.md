# Пингвин в настройках Pengram: средний размер вместо мелкого

Дата: 2026-10-22 · ветка `arena/c8e4a10f-telegram`

## Жалоба

«В настройках → Pengram пингвин слишком мелким стал. Не нужно его делать
огромным, но мелким тоже не надо». Область, подтверждённая пользователем:
**оба** экрана — компактная шапка корня настроек и большое превью в разделе
«Пингвин».

## Что изменено

`TMessagesProj/src/main/java/org/telegram/ui/PengramSettingsActivity.java`,
внутренний класс `PengramHeaderView`:

| Константа | Было | Стало | Где |
|---|---|---|---|
| `BASE_SIZE_DP` (превью, ползунок 100%) | 224 | **256** | `buildFull` → `clampPenguinSize` |
| компактная шапка корня | `dp(72)` | **`dp(96)`** | `buildCompact` |

Больше ничего не тронуто: камера `PengramPenguinView` (FOV 34°, `BODY_FILL`,
`CAM_FILL`, `CAM_MARGIN`, `CONTENT_BOTTOM`, запас глубины и условный резерв
прыжка) осталась прежней, ползунок 70…150% работает как раньше,
`clampPenguinSize` по-прежнему ограничивает кадр шириной строки и высотой
экрана минус 240dp с полом `dp(96)`, компактная шапка по-прежнему игнорирует
ползунок, слоты пингвина в плеере (132dp MINI / 160dp LYRICS) не менялись.

## Почему увеличен контейнер, а не камера

Квадратный вьюпорт подгоняется под «конверт» содержимого, поэтому цель
`BODY_FILL = 0.84` на практике не связывает — расстояние до камеры задаёт
огибающая «тело + аксессуар + запас глубины ради перспективы». Аналитическая
модель по реальным вершинам `buildMeshes()` (скин без аксессуара, покой):

```
тело:            minY -1.005 … maxY 1.175        → bodyHeight 2.18
конверт:         top 1.175 + 0.035 = 1.21
                 bottom -1.11 - 0.035 = -1.145   → fitHeight 2.355
глубина:         max(0.75, radiusXZ ≈ 0.766)     = 0.766
bodyDistance  = (2.18 / 0.84 · 0.5) / tan17°      = 4.244   ← не связывает
fitDistance   = 0.766 + (2.355 / 0.98 · 0.5)/tan17° = 4.696 ← связывает
видимая высота кадра = 2 · 4.696 · tan17°         = 2.872
доля тела по высоте  = 2.18 / 2.872               ≈ 0.759
доля тела по ширине  = 1.28 / 2.872               ≈ 0.446
```

То есть доля кадра почти постоянна (≈0.759 по высоте) и не зависит от
`BASE_SIZE_DP`; высокий колпак уменьшает её ещё сильнее. Значит единственный
предсказуемый рычаг видимого размера — dp контейнера. Крутить `BODY_FILL`,
`CAM_FILL`, `CAM_MARGIN` или пол глубины 3.2 бессмысленно: они не связывают,
а их ослабление резало бы клюв, лапы и тени без выигрыша в размере.

## Что это даёт на экране

Рост видимого тела = dp кадра × 0.759 (аналитика, не замер пикселей):

| Экран | Кадр было → стало | Тело было → стало | Линейно |
|---|---|---|---|
| Превью, ползунок 70% | 156.8 → 179.2dp | 119 → 136dp | +14.3% |
| Превью, ползунок 100% | 224 → 256dp | 170 → 194dp | +14.3% |
| Превью, ползунок 150% | 336 → 384dp | 255 → 291dp | +14.3% |
| Компактная шапка корня | 72 → 96dp | 55 → 73dp | +33.3% |

Плюс по площади: превью +30.6%, компактная шапка +77.8%. «Средний» характер
изменения зафиксирован контрактом в `scripts/test-pengram-penguin-geometry.py`:
база обязана лежать в 240…300dp, компактная шапка в 88…112dp, тело превью при
100% в 185…205dp, при 70% не ниже 125dp, при 150% не выше 300dp, тело
компактной шапки в 65…85dp. Это защита в обе стороны: ни отката к 72/224, ни
уезда в «огромный».

## Вёрстка

Шапка превью при 256dp занимает примерно 256 + реплика + заголовок + версия +
ссылки + отступы ≈ 420dp — меньше половины типового экрана (≈800dp), список
разделов остаётся видимым. На коротких экранах и в split-screen кадр
ограничивает `clampPenguinSize`: `min(ширина строки − 32dp, высота экрана −
240dp)` с полом `dp(96)`, поэтому переполнения нет. Компактная шапка выросла
на 24dp по высоте — это цена узнаваемого персонажа вместо значка; композиция
(центрирование, ссылки в строку) не менялась.

  пол clamp), поэтому матрица не может разойтись с UI.

  `test-pengram-penguin-header.py`, `test-pengram-profile-smooth.py`
  (256dp / `dp(96)`), инвариант «без density²» сохранён.
- Все 60 сюитов `scripts/test-pengram-*.py` — exit 0.
- `python3 scripts/gen-pengram-audit.py` (инвентарь пересобран: номера строк
  в `PengramSettingsActivity.java` съехали) + `test-pengram-audit-clean.py` — PASS.
- CI: preflight (компиляция Java, слияние ресурсов APK, все сюиты) и сборка
  ARM64 APK — см. статусы прогонов в истории ветки.

**NOT RUN / не доказано здесь:**

- Замеров на устройстве и пикселях нет: Android-устройства, эмулятора и GL
  в этой среде нет, поэтому 0.759 и все dp-числа выше — аналитика по вершинам
  и исходникам, а не скриншоты.
- Поведение в анимированных позах (танец, прыжок, сальто, взмах крыла,
  моргание) не проверялось: модель описывает статический кадр, как и прежние
  тесты камеры.
- Требование «≥52/92/112dp для каждого скина» и граница «70% ползунка
  ≥0.62×256dp» из старого аудита по-прежнему **не установлены**: с высокими
  аксессуарами (колпак волшебника, maxY ≈ 1.97) доля тела падает ниже 0.759.
- Исторические цифры 72dp/224dp в `docs/pengram-audit-2026-10-22.md` —
  снимок того аудита, они намеренно не переписаны.

## Откат

Две строки: `BASE_SIZE_DP = 256` → `224` и `final int size = dp(96)` →
`dp(72)` в `PengramSettingsActivity.java`, плюс контракты размеров в четырёх
сюитах. Камера и `PengramConfig` не менялись, так что сохранённый у
пользователя процент ползунка означает то же, что и раньше.
