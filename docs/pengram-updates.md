# Обновления Pengram без своего хостинга

Документ описывает **план**, а не реализацию: по просьбе проверка обновлений,
уведомление и кнопка «Проверить обновления» в этом изменении не добавлялись.
Здесь собрано всё, что нужно, чтобы сделать это бесплатно, надёжно и без
собственного сервера.

## 1. Что требуется

- красивое уведомление «доступно обновление»;
- отдельная кнопка «Проверить обновления» (одна, в настройках Pengram);
- никакого собственного хостинга и никаких ежемесячных платежей;
- сборка APK уже происходит в GitHub Actions, поэтому логично, чтобы оттуда же
  приходило и обновление.

## 2. Рекомендуемая схема: GitHub Releases как сервер обновлений

Репозиторий уже публичный, а workflow `.github/workflows/build-android-arm64.yml`
уже публикует APK по тегу `build-*` (шаг `softprops/action-gh-release`). То есть
**сервер обновлений уже существует** — это страница релизов GitHub. Остаётся
только научить приложение её читать.

Почему это лучший бесплатный вариант:

| Свойство | Значение |
| --- | --- |
| Цена | 0 |
| Размер файла | до 2 ГБ на ассет (APK ~60–120 МБ проходит с запасом) |
| Трафик | не тарифицируется и не ограничен |
| HTTPS и CDN | из коробки |
| Метаданные | версия, дата, changelog, размер, `sha256` (`assets[].digest`) |
| Публикация | уже автоматизирована тегом `build-*` |

### Эндпоинты

```
GET https://api.github.com/repos/<owner>/<repo>/releases?per_page=5
GET https://api.github.com/repos/<owner>/<repo>/releases/latest
```

Из ответа нужны: `tag_name`, `name`, `body` (changelog), `published_at`,
`prerelease`, `assets[] { name, size, browser_download_url, digest }`.

Лимит без токена — 60 запросов в час на IP. Приложение делает 1 запрос при
запуске (не чаще раза в 6–24 часа) и 1 по нажатию кнопки, поэтому лимит
недостижим. Ответ кэшируется по `ETag`: при `304 Not Modified` тело не
передаётся вовсе.

### Резервный канал без API

Если GitHub API недоступен (мобильные операторы в РФ периодически его
замедляют), второй источник — обычный файл в репозитории:

```
https://raw.githubusercontent.com/<owner>/<repo>/main/update.json
```

```json
{
  "versionCode": 6012,
  "versionName": "6.1.2",
  "minSupported": 5900,
  "channel": "stable",
  "notes": "…",
  "apk": "https://github.com/<owner>/<repo>/releases/download/build-6012/Pengram-arm64.apk",
  "sha256": "…",
  "size": 104857600
}
```

`raw.githubusercontent.com` раздаётся через CDN, без лимитов API и без токена;
jsDelivr (`https://cdn.jsdelivr.net/gh/<owner>/<repo>@main/update.json`) — третье
зеркало того же файла. Порядок опроса: API → raw → jsDelivr, первый успешный
ответ выигрывает.

### Почему не альтернативы

| Вариант | Почему не подходит |
| --- | --- |
| Cloudflare Pages / Netlify | лимит 25 МБ на файл — APK не влезает |
| jsDelivr для APK | лимит 20 МБ на файл |
| Firebase Hosting | бесплатно 10 ГБ/мес, но нужен проект Google и ручная загрузка APK |
| Telegram-канал | нет стабильного URL файла и машиночитаемой версии; парсинг `t.me/s/` хрупок |
| Google Play | подпись, модерация и правила магазина — форк туда не попадёт |
| Свой VPS | это и есть хостинг, которого нет |

## 3. Клиентская часть

### 3.1. Класс `PengramUpdates` (`org.telegram.messenger`)

- `check(boolean manual, Callback)` — сеть в `Utilities.globalQueue`,
  результат в UI-поток.
- Сравнение версий — по `versionCode` (`BuildConfig.VERSION_CODE`), а не по
  строке: строки вида `6.1.2` и `6.1.10` сравнивать нельзя.
- Кэш в `SharedPreferences` (`pengram_updates`): последний удачный JSON, `ETag`,
  время проверки, «версия, о которой уже уведомили».
- Автопроверка: не чаще раза в 24 часа и только по Wi-Fi/зарядке (по желанию),
  с настройкой «проверять автоматически».
- Никакой телеметрии: запрос не содержит идентификаторов аккаунта.

### 3.2. Кнопка «Проверить обновления»

Одна строка в настройках Pengram (раздел «О приложении» / «Обновления»), а не
дубль в нескольких местах. Состояния: «Проверяю…» → «Установлена последняя
версия (6.1.2)» либо «Доступна версия 6.1.3» с переходом на экран обновления.

### 3.3. Уведомление

- Отдельный канал `pengram_updates` (важность `DEFAULT`, звук — тихий,
  вибрация — по желанию), чтобы не смешивать с сообщениями.
- Стиль: `BigPictureStyle` с обложкой релиза (или `BigTextStyle`, если обложки
  нет), заголовок «Доступно обновление Pengram», текст «6.1.3 · 12,4 МБ»,
  действие «Скачать».
- Один показ на версию: повторно не уведомлять, пока версия не сменится.
- Тап открывает экран обновления внутри приложения, а не браузер.

### 3.4. Экран обновления (MD3, в стиле остальных экранов Pengram)

- Шапка: иконка приложения, «Pengram 6.1.3», дата, размер, `SHA-256` (сокращённо).
- Changelog из `body`: минимальный markdown-парсер (заголовки, списки, `**жирный**`,
  ссылки) — без внешних библиотек.
- Кнопка «Скачать» с прогрессом и «Отмена»; после скачивания — «Установить».
- Если версия ниже установленной или канал `prerelease` при отключённой бетe —
  экран честно говорит, что обновления нет.

### 3.5. Скачивание и установка

1. `DownloadManager` (системный, с докачкой и своим уведомлением) либо
   `FileLoader` с прогрессом в приложении — первый проще и переживает
   перезапуск.
2. Файл кладётся в `Downloads/Pengram-<version>.apk` (не во внутреннюю папку,
   чтобы пользователь мог поставить вручную).
3. Перед установкой обязательно:
   - сверить `sha256` с метаданными релиза;
   - сравнить подпись скачанного APK с подписью установленного
     (`PackageManager.getPackageArchiveInfo(path, GET_SIGNING_CERTIFICATES)`);
     при несовпадении — не предлагать установку и объяснить причину;
   - разрешить установку из этого источника (`REQUEST_INSTALL_PACKAGES`).
4. Установка: `PackageInstaller` (сессия) на Android 12+, `Intent.ACTION_VIEW`
   с `application/vnd.android.package-archive` через `FileProvider` — на старых.
5. Никогда не устанавливать молча: только по нажатию.

### 3.6. Безопасность

- Только HTTPS и только хосты `api.github.com`, `raw.githubusercontent.com`,
  `cdn.jsdelivr.net`, `github.com`, `objects.githubusercontent.com`.
- APK принимается только при совпадении `sha256` **и** подписи.
- Никаких редиректов на сторонние хосты: `HttpURLConnection` с ручной проверкой
  `Location`.
- Подпись сборки не должна меняться между релизами, иначе обновление «поверх»
  не встанет — за этим уже следит шаг `Verify signing schemes` в CI.

## 4. Что добавить в репозиторий

1. `docs/CHANGELOG.md` — человекопонятный список изменений.
2. В workflow (шаг `Publish beta release`) — `body_path: docs/CHANGELOG.md`
   вместо `generate_release_notes`, чтобы текст в приложении был осмысленным.
3. `update.json` в корне (обновляется тем же workflow через `git push` в
   отдельную ветку или ботом) — только если нужен резервный канал.
4. `versionCode` в `TMessagesProj_AppStandalone` — уже есть; договориться о
   схеме нумерации (например, `major*10000 + minor*100 + patch`).

## 5. Порядок работ

| Шаг | Объём | Результат |
| --- | --- | --- |
| 1. `PengramUpdates` + кэш + ETag | ~200 строк | проверка версии работает |
| 2. Строка «Проверить обновления» | ~60 строк | ручная проверка |
| 3. Уведомление и канал | ~120 строк | «красивое» уведомление |
| 4. Экран обновления | ~300 строк | changelog, размер, sha |
| 5. Скачивание + установка + проверка подписи | ~250 строк | обновление в один тап |
| 6. Тесты (`scripts/test-pengram-updates.py`) | ~80 строк | регрессии не пройдут |

Итого — примерно один крупный экран и один сервисный класс; хостинг не нужен
ни на одном шаге.

## 6. Риски и как их снять

- **GitHub API недоступен.** Резервный `update.json` на raw/jsDelivr и
  «тихий» режим: если проверить не удалось, приложение молчит, а кнопка
  показывает «Не удалось проверить, попробуйте позже».
- **Пользователь обновляется вручную.** Кнопка проверки — не единственный путь:
  ссылка на страницу релизов всегда доступна на экране «О приложении».
- **Ложное «нет обновлений» из-за кэша CDN.** `ETag` + `Cache-Control: no-cache`
  в запросе к API; для raw-файла — параметр `?t=<timestamp>`.
- **Разные подписи у сборок.** Обновление поверх не встанет; проверка подписи
  покажет это до скачивания, а не после.
